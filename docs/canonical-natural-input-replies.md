# 정본 대화에서 자연어로 API 입력 답하기

미배포 소스 기능이며 npm 0.2.0에는 포함되지 않습니다. 공식 `createWorkflowDraftConversationGraph`가 API 필수 입력을 질문했을 때 구조화된 값 대신 자연어로 답할 수 있습니다. 기존 `answer-inputs`도 그대로 사용할 수 있습니다.

```ts
const result = await graph.invoke(
  new Command({
    resume: {
      action: 'reply-inputs',
      token: currentBoundary.token,
      messageId: 'user-answer-2',
      text: '상품번호는 문자열 "fixture-canonical-01"이야.',
    },
  }),
  config,
);
```

응답은 현재 질문 토큰과 새 메시지 ID를 사용해야 합니다. `reply-inputs`는 실제 `api-input` 질문이 있을 때만 `actions`에 표시됩니다. 검토·요구사항 구체화·범위 변경을 API 값 답변으로 처리하지 않습니다. 요청을 바꾸려면 기존 `revise`를 명시적으로 사용합니다.

## 처리 흐름과 책임

`awaitQuestions`에서 받은 답변은 별도 `extractInputAnswers` 체크포인트 노드로 갑니다. 이 노드는 공개 함수 `analyzeApiInputAnswers`에 현재 미확정 OAS 입력 계약과 실제 원문만 전달합니다. API 선택·바인딩·입력 생성 모델을 다시 실행하지 않습니다. 추출은 `interrupt` 안에서 실행하지 않습니다.

모델은 입력 ID와 원문 구간을 선택하고, Core가 타입을 유지하며 파싱·OAS 검사·누락 목록·일치 위치를 계산합니다. 설명을 끈 경우에도 `analysis.sources`는 반환됩니다. 이 자료는 검증에 필요한 선택 근거이며 모델 이유를 새로 요구하는 옵션은 아닙니다. `includeExplanations`를 켜면 같은 호출에서 짧은 이유를 추가로 받습니다. [공통 추출 계약](api-input-answer-extraction.md)을 참고하세요.

`applyResponse`의 API 입력 처리 함수는 현재 원문·질문·계획 토큰과 추출 당시 자료를 다시 대조합니다. Core에서 같은 원문 선택을 다시 해석한 값·위치·누락 목록과 같아야 적용합니다. 선택적 설명 기록도 실제 적용 결과와 같아야 합니다. 저장된 값이나 파싱 완료 표시만 신뢰하지 않습니다.

정상 답변은 기존 구조화 입력과 같은 결정적 적용 경로를 사용합니다. 이전 바인딩과 원래 입력 제안을 재검사하고, 명시적으로 확정한 값만 추가합니다. 전체 API 입력 생성이나 의미 계획을 재호출하지 않습니다. 이후 연결 계획 등 아직 필요한 단계는 원래 절차대로 실행합니다.

## 답변과 계획의 수명

사용자 원문은 `messages`에 그대로 남기며 구조화된 직접 입력인 것처럼 다시 라벨링하지 않습니다. `inputAnswerHistory`에는 응답 ID, 현재 질문 토큰, 최초 입력 계약, 추출 결과가 남습니다. 적용 대기 중의 `inputAnswerExtraction`은 적용 후 지웁니다. 기록은 다음 의미 계획의 입력이나 최종 n8n JSON에 넣지 않습니다. 원문·실제 값이 포함되므로 호스트가 메모리·보관 기간·접근 권한을 정해야 합니다.

입력값이 없는 답변이면 질문·계획을 유지하고 값을 명시하거나 `revise`를 사용하도록 안내합니다. 일부 값만 답하면 나머지만 질문하며 앞서 확정한 값과 기록은 유지합니다. 오래된 토큰·중복 메시지 ID·잘못된 응답 경계는 모델 호출 전에 거절합니다. 빈 채팅 메시지는 거절하지만, API의 빈 문자열은 원문에 `""`처럼 명시하면 OAS가 허용하는 한 값으로 처리할 수 있습니다. 공백이나 타입을 임의로 바꾸지 않습니다.

이 기능은 원문 존재와 OAS 적합성을 검사합니다. 사용자의 의미적 의도, 제공자 신원이나 변경되지 않은 저장소 자체를 인증하는 기능은 아닙니다. 모델의 잘못된 출력·존재하지 않는 원문 구간·OAS 위반은 보정하거나 숨은 재시도로 처리하지 않습니다.

## 불필요한 바인딩 호출을 생략하는 조건

실제 ICL 짧은 요청 검증 중, 선택한 API 외에는 아무 생산자도 없는데 바인딩 모델이 선행 응답과 직접 입력 중 하나를 고르도록 질문한 사례를 확인했습니다. 현재는 다른 선택된 API/native 인스턴스도 없고, 실제 출력 후보도 없고, 바인딩 단계가 소유한 미확정 소스 요구도 없을 때 코드가 빈 바인딩을 확정합니다. 필요한 리터럴 값은 입력 생성·질문 단계의 책임으로 남깁니다.

아직 구현 재료를 받지 못한 생산자가 선택되어 있으면 `hasOtherSelectedNodes`에 포함합니다. 후보 계약이 아직 없다는 이유로 이 조건을 통과시키지 않습니다. 명시적인 바인딩 미확정 요구도 생략하지 않습니다. 이름이 같은 값을 자동 연결하거나 미입력 값을 만들어 주는 로직은 아닙니다.

## 확인한 실행과 한계

전체 ICL OAS를 제공하고 “상품 단건 기본 정보를 조회하는 워크플로우를 만들어줘.”로 시작했습니다. 사용자가 API 선택을 검토한 뒤 상품번호를 자연어로 답하고 후보를 승인했습니다. Chomsky 호출 네 번으로 의미 선택·입력 제안·원문 추출·연결 계획이 진행됐고, 같은 계획의 SDK JSON을 격리 n8n에서 실행했습니다. 로컬 Bearer credential과 요청값·OAS 응답 계약을 검사했으며 실제 ICL 서비스는 호출하지 않았습니다.

초기 실행은 위의 불필요한 바인딩 질문에서 중단됐고 그 실패 산출물을 보존했습니다. 코드 변경 뒤 새 실행이 성공한 것이며 최초 실행 실패를 통과로 바꾸거나 모델 결과를 수선한 것이 아닙니다. 이 한 사례는 일반적인 다중 서비스·모든 native 기능·장기간 대화의 성공률을 뜻하지 않습니다.
