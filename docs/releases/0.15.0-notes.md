# v0.15.0

This release preserves repeated API call instances when one human choice selects their shared API alternative. It also exposes capability output-reference protocols before native role and producer selection.

An `operation-call-choice` question declares `callPurposes` separately from its API alternatives. One selected API creates one call instance per declared purpose. Existing single-choice and multiple-choice questions retain their semantics. Counts are never inferred from prose, and missing call roles, stale alternatives and mismatched answers are rejected. LangChain supplies a distinct strict structured-output variant, and question identity includes the declared call purposes.

Native planning material now distinguishes accepted parameter-reference kinds from potential output-reference kinds. Core derives the latter from registered output-schema factories and exclusive-output ports. These are protocols, not fabricated output schemas: only configured, validated producers authorize actual data references. LangChain exposes the selected protocols without an additional model call or feature-name exclusions.

Packages: [Core](https://www.npmjs.com/package/@openapi-flow/core/v/0.15.0), [LangChain](https://www.npmjs.com/package/@openapi-flow/langchain/v/0.15.0), [n8n](https://www.npmjs.com/package/@openapi-flow/n8n/v/0.15.0).

## Compatibility

Consumers with exhaustive switches over `ApiSelectionQuestion` must handle the new `operation-call-choice` kind as a single API answer with multiple explicit call purposes. `NativePlanningCapabilityMaterial` gains the required code-owned `potentialOutputReferenceSources` field. Do not construct substitute planning contracts or treat this field as a configured output schema. Source-bound planning receipts must be regenerated when their material changes. All three package versions are aligned; the n8n adapter's execution behavior is unchanged.
