## Fixed API results

`N8nNativeFeature.GatherApiResponses` and
`createApiResponseResultsCapability({ materials })` expose `gather-api-responses`.
The model selects only `sourceNodeIds` from real API call instances. Code owns
`{ results: [{ callId, documentId, method, path, body }] }`, derives provenance
from original operation contracts and preserves each complete response body.
Document IDs come from host OAS registration, not an invented OAS property.
Different invocations of one operation keep distinct call IDs. Missing operation
IDs do not require generated names or fallback identifiers.

The compiler uses official SDK Merge Append for multiple sources, the shared
full-response OAS guard and official Aggregate All Item Data with fixed `results`.
One source needs no Merge. The output schema derives full body constraints and
requires exactly one entry per selected call, independent of array position.
No name generation, field renaming, response projection, casts, fabricated values,
model-output repair or hidden retries are added. Exactly one response item per
selected API invocation is required; item-wise batch joining is a separate feature.

Wait-only branch joins and response checks retain Merge and original API response
references. Result reconstruction is not a mandatory workflow step. Downstream API
bindings should retain original call IDs and OAS response pointers, not infer
source identity from a consolidated list index.

## Security publication blocker (2026-10-24)

The initial aligned release gate passed deterministic and isolated runtime checks
but failed `npm audit`: nine affected dependency packages, six High and three
Moderate. This is a dependency advisory inventory, not evidence of an attack.
The owner selected security remediation and verification before publication.

Supported updates remove the fast-uri URL-parsing advisories and the undici
process-termination advisory and update our public Zod 4 boundary. Normal package
installation updated the lockfile without force, overrides, patched dependencies,
audit omissions, an arbitrary downgrade or new OAS/data restrictions.

The subsequent production audit reports five High affected packages and no
Moderate warnings, all from one remaining Zod advisory: `@n8n/config`,
`@n8n/expression-runtime`, `@n8n/workflow-sdk`, `n8n-workflow` and their Zod 3.
The installed SDK 0.36.4 pins Zod 3.25.76; registry metadata for the latest SDK
0.37.2 also pins 3.25.76, as does the latest `@n8n/config` 2.42.1.
Zod's upstream issue remains open, and its maintainer says no new v3 versions
will be published while disputing the vulnerability classification. The advisory
still applies; neither that disagreement nor a host Zod 4 update clears this gate.

A bounded two-element local probe confirmed that SDK-owned Zod 3 visits both
entries and produces three issues despite `.max(1)`. Host Zod 4.6.7 rejects an
oversized array, set and map before visiting entries, producing one size issue.
This verifies the dependency behavior, not an exploit through an application
endpoint. Unbounded inputs and actual application exposure are not established
by this probe. No dangerous memory-exhaustion test was run.

The original security-first decision blocked publication. On 2026-10-25 the owner
explicitly accepted this remaining advisory as a release limitation and authorized
source-first publication and Qoopilot installation. A fresh audit still reports
five High affected packages from this one advisory; it is not a clean audit.
Latest SDK metadata still pins Zod 3.25.76. No forced Zod 4 replacement, advisory
exclusion, dependency override or downgrade is part of this acceptance. Actual
application exploitability has not been established. Service deployment is not
included in the authorization.

Sources: [Zod advisory](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5),
[official Zod v3 issue](https://github.com/colinhacks/zod/issues/6653),
[undici advisory](https://github.com/advisories/GHSA-xjj6-f33q-929c),

## Source-owned error contract and enum error context

This candidate also adds `OpenApiFlowError`, the public browser-safe
`@openapi-flow/core/errors` entry point and shared diagnostic schemas/types.
OAS validation, API selection/binding planning, existing native/graph planning
errors and planned/template n8n compilation expose the observed source boundary.
Original exceptions remain in `cause`; private model output, raw messages and
stacks are not in the diagnostic JSON. Hosts attach their own run context and
localized presentation. Not every internal throw or provider timeout is migrated.
Existing error subclasses retain their identities and failure payloads.

The optional enum helper now validates initial provenance synchronously before
its asynchronous enum call. Invalid initial arguments retain their correct
argument-stage failure and original output; enum transport errors are not
relabelled or retried. Request values and their original types remain unchanged.

Before this publication request, final sequential checks passed strict workspace
types, lint, formatting, 45 focused error/evaluation/checkpoint regressions,
55 original-OAS checks, one 170-operation multi-document coverage regression,
browser bundling/execution without Node polyfills and independent strict packed
consumer installation. The complete suite passed 1,287/1,288; its single failure
is the unchanged accepted Ajv special-key limitation, with no skipped/cancelled
tests. Loopback ChatOpenAI transport tests made four requests, without retries;
they are not a replay or diagnosis of a historical Chomsky failure.
