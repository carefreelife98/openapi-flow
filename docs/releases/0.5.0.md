## Changes and compatibility

Connection outlines now retain the complete session goal inventory in `goalIds`.
Core derives bundle associations from typed goals and actual node anchors, keeps
semantic and cross-bundle work in `globalGoalIds`, and records each stored
bundle's `scope` as `local` or `global`. Model-supplied trace IDs do not establish
goal coverage or satisfaction. Finishing local graph bundles does not bypass
whole-session completion checks.

This is a breaking stored-outline contract change. Regenerate outlines saved by
older versions from the original current source and accepted session. Do not fill
in missing fields, silently migrate old snapshots or treat trace metadata as
proof of completion. Existing outline fingerprints and source/session validation
remain part of the boundary.

`planWorkflowConnectionStep` accepts optional `allowMaterialRevisions`, defaulting
to `false`. Omitted and explicit `false` retain the previous model wire contract;
`true` enables a request to replan eligible existing materials. Core exports
`createWorkflowConnectionMaterialRevisionRequest` and
`validateWorkflowConnectionMaterialRevisionRequest` to bind that request to the
current source, session, revision and eligible stage/node targets. They reject
stale or out-of-scope requests and do not adopt materials or mutate the graph.
The host must dispatch originating-stage planning and use the existing revision
API to validate and adopt compatible source and graph together. Automatic host
dispatch is not claimed as integrated in this candidate.

Native producer selection now grants access to permitted source materials.
Actual parameter references may use a subset, including no sources; selecting a
producer does not create an execution dependency. Unselected sources and invalid
pointers, kinds or types still fail validation. LangChain pools exactly repeated
native-selection material contexts on the model wire while preserving original
schemas, values, identities, receipts and validation.

The existing numeric-query HTTP Request pagination candidate is present in the
reviewed workspace and is included in this candidate scope if retained in the
final release source. It is an explicit compiler option using the official n8n
HTTP Request pagination settings. The bounded numeric sequence is checked
against the original OAS contract, with explicit request-budget or status-code
termination and original per-page response envelopes. It does not imply fetching
every record, collecting pages into a body or model/host pagination planning.
Generic IF/conditional-loop planning and compilation, body-parameter pagination,
response-body/empty-body termination and next-URL traversal are expressly
excluded. Pagination source and execution evidence remain owned by the earlier
task and must be preserved in the final source review.

## Known dependency security limitation

The 0.4.6 release record and public notes retain the upstream High dependency
warning. The earlier detailed record in `docs/releases/0.3.14.md` identifies the
same Zod 3 advisory and the owner's acceptance; 0.4.5 records the same five High
entries. The release operator supplied a fresh 2026-10-28 audit for this candidate: High 5;
Info, Low, Moderate and Critical all 0. This audit was not rerun by the preparation
task.

The five affected package entries are `@n8n/config`,
`@n8n/expression-runtime`, `@n8n/workflow-sdk`, `n8n-workflow` and their Zod 3,
associated with [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5).
They are affected dependency entries from the same advisory, not five distinct
vulnerabilities or demonstrated application exploits. The unchanged lockfile
retains SDK 0.36.4, config 2.41.2, expression-runtime 0.34.2, n8n-workflow 2.43.4
and the SDK/config/expression Zod 3.25.76 contracts. The release operator reports
`fixAvailable: false` for the SDK in this audit; that result does not establish a
universal absence of fixes or application exploitability.

This is the previously accepted unresolved limitation, not a new Task 4
dependency change or a clean audit. No third-party version, Zod 3-to-4 override,
SDK downgrade or advisory exclusion is introduced. The release operator checks release
source and audit provenance before publication.
