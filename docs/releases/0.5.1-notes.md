# openapi-flow 0.5.1

API binding planning now selects source/target candidates derived from the
original OpenAPI and native contracts. Code copies declared property paths and
node identities. The model supplies candidate choices and explicit array-index,
dictionary-key or open-path selectors. The returned binding-plan format stays
compatible with 0.5.0; existing reference, type, route and DAG checks still run.

Core exports `describeApiBindingCandidates`, `resolveApiBindingCandidates` and
`listWorkflowRequiredPrecedence`. Required precedence describes confirmed data
references and declared dependencies, including input-port scope. It does not
create edges or infer business order from the API selection list.

LangChain exports `ApiCallBindingPlanningError` and
`createApiCallBindingRejection`. Hosts can use snapshot-bound rejection feedback
to correct one rejected call within their own explicit budget. The primitive
does not retry automatically. Network failures are not binding-repair feedback.
The LangGraph example demonstrates bounded host composition.

HTTP Request compilation also resolves the effective OAS server in operation,
path, then document order, using the first server and declared variable
defaults. A non-absolute address is exposed as a deployment requirement.
Existing explicit deployment inputs remain available to library consumers.
Connection goal review distinguishes deployment preparation from business goals.

## Compatibility and verification scope

All three packages and their internal dependencies are aligned at 0.5.1.
Third-party dependency versions are unchanged. Public binding receipts retain
their format, but the internal model output schema now uses candidate choices.
Custom model fixtures must respond to that schema. The connection-planning
description gains `requiredPrecedence`; consumers persisting an older description
should regenerate it from the original source.

Focused checks cover candidate coupling, dynamic selectors, native/recursive
contracts, stale feedback, bounded correction and independent-call scheduling.
Actual model transport accepted the strict schema. Isolated n8n verification
uses incremental planning only. These checks do not establish success for every
natural-language request or real business-service execution. Host adoption is
verified separately after publication.

Candidate type compatibility does not prove business meaning, field presence or
complete JSON Schema subsumption. A real-spec probe selected a different
same-type field than the evaluator expected; that semantic mismatch remains an
open quality issue. No automatic first-item choice, same-name mapping or value
coercion is introduced. Generic IF loops and body/next-URL pagination remain
outside this release.

The accepted Ajv `__proto__` validation limitation remains unresolved. The
unchanged n8n SDK dependency graph also retains the previously disclosed Zod 3
advisory [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5).
This release does not claim a clean full suite or a clean security audit.

Source verification and publication evidence are recorded in `0.5.1.md`.
