# 짧은 멀티턴 대화 평가

## 짧은 요청 12턴의 재평가와 계약 경계 수정

원본 Member·ICL 188개 후보로 기존 네 시나리오의 12턴을 새로 생성했다. 실제 모델
40회에서 10턴은 통과하고 2턴은 실패했다. 통과한 10턴은 격리 n8n에서 11회 실행해
로컬 계약 서버를 18회 호출했다. 응답 재생·재시도·실서비스 호출은 없었다. 이미
사용한 계약·시나리오이므로 처음 보는 서비스의 성공률이나 출시 합격선으로 보지 않는다.

| 시나리오                                                            | 관측 결과                                         |
| ------------------------------------------------------------------- | ------------------------------------------------- |
| 회원 조회 → 입력 답변 → 주소 추가 → 최초 값 수정 → 주소 취소        | 4턴 통과                                          |
| 회원 조회 → 응답 기반 뉴스레터 본문 추가 → 숫자 값 수정 → 변경 취소 | 4턴 통과                                          |
| 두 서비스 조회 → 결과 합류·응답 검사 → 상품 조회·검사 제거          | 앞의 2턴 통과, 마지막 연결 검사 실패              |
| 요구 구체화를 켠 미지원 이력 조회                                   | 원본 계약 검사와 실행용 계약의 혼용으로 출력 실패 |

기록은 `.local-artifacts/canonical-short-evaluation/1792395083290-98115/`에 있다.
회원번호가 없는 최초 질의에는 실제 질문을 받고 준비한 자연어 답변을 제출했다.
후속 요청은 API의 응답 회원번호를 사용했으며 최초 입력을 복사하지 않았다. JSON
본문의 숫자 `1`을 `0`으로 수정하고 변경 API를 취소하는 경로도 원래 타입을 유지했다.

이력 조회의 오류는 n8n 변환 전에 원본 계획용 계약을 실행용 계약으로 바꾸면서
발생했다. 원본 구체화 기록은 원본 계약에 연결돼 있으므로 변경된 계약으로 검사하면
오래된 기록으로 판정된다. 이제 검토·준비 상태·결손 근거는 원본 계약으로 검사하고,
실행용 계약은 별도 입력으로 노드 변환에만 전달한다. 검사를 생략하거나 기록을 새로
발급하지 않는다. 위조한 원본 지문도 계속 거절한다.

최초 실패의 모델 응답 3개는 기록된 입력·스키마가 같은지 검사한 뒤 그대로 재생했다.
이번에는 같은 경로에서 경고 JSON을 출력하고 격리 n8n에서 Start만 실행했다.
실제 모델·HTTP 호출은 0회였다. 수정 검증 기록은 `1792395822000-1497`이며 새로운
생성 성공률에 합산하지 않았다. 별도의 새 호출은 추가 구체화 질문에서 멈춰 수정
지점에 도달하지 않았다. 원래 보고서는 즉시 출력을 기대해 실패로 기록했으나,
독립 감사에서 사용자 답변 대기임을 확인했다. 원래 보고서는 수정하지 않았다.

한국어 입력 답변의 이유 두 문장이 영어였던 점은 같은 설명 생성 단계의 프롬프트와
스키마 설명에 사용자 언어 지시를 추가해 보강했다. 한국어·일본어·영어와 값 미제공
네 사례를 실제 모델로 확인했으며 원문 값·타입·근거는 유지했다. 별도 번역 호출이나
문자 종류를 이용한 운영 중 거절 규칙은 없다. 제한된 사례의 언어 관측 결과다.

상품 조회 삭제의 연결 실패는 아직 남아 있다. 삭제한 노드의 연결선이 남았고 기존
2입력 Merge도 남은 상태였다. 최종 검사가 이를 거절했지만, 반드시 제거할 연결선까지
모델에게 맡긴 책임 배분은 보강해야 한다. 남은 응답을 복제하거나 Merge 설정·노드를
임의로 바꿔 통과시키지는 않았다.

## 미지원 요청의 명시적 결손 보존

원본 Member·ICL의 188개 API 후보와 등록 native 기능을 제공하고 실제 Chomsky를
5회 호출했다. 두 시나리오·세 턴에서 정상 조회 1턴과 명시적 미해결 2턴을 확인했다.
재생·재시도·실서비스 호출은 없었다. 기존 조회의 요청값·바인딩을 변경하거나 없는
API를 다른 작업으로 대체하면 실패하도록 검사했다.

1. `회원번호 "fixture-member-01"의 뉴스레터 수신 설정 변경 이력을 조회해줘. 이력 API가 없으면 다른 작업으로 대신하지 마.`
2. `회원번호 "fixture-member-01"의 간단 정보를 조회해줘.`로 시작한 뒤
   `회원 간단 정보 조회 다음에 뉴스레터 수신 설정 변경 이력도 조회해줘. 이력 API가 없으면 기존 조회는 유지하고 그 다음 위치에 미해결 단계를 표시해줘. 설정 변경이나 로그인 이력으로 대신하지 마.`라고 추가했다.

첫 사례는 결손만 있는 실제 n8n JSON을 반환했다. 둘째 사례는 최초 회원 조회를
로컬 계약 서버에서 실행한 뒤, 후속 대화에서 그 API와 요청값을 보존하고 그다음
위치에 결손을 연결했다. 두 결손 결과에는 원문 근거·실제 제공된 계약 목록·한글
판단 이유가 남았으며 Start는 분리됐다. 분리된 JSON의 n8n 실행은 Start만 수행하고
HTTP 요청을 보내지 않았으므로 업무 성공이 아닌 출력 안전장치 확인으로 분류했다.

원본 모델 입력·출력과 최종 초안·import JSON·실행 요약은
`.local-artifacts/canonical-short-evaluation/1792393790375-92432/`에 있다. 별도의
결정적 실행 검증은 `.local-artifacts/capability-gaps/1792393788974-92411/report.json`
에서 확인한다. n8n 2.37.10의 네 사례 중 기본 Start 분리 두 건은 요청 0회였고,
검증용으로만 Start를 다시 연결한 두 건은 대역에서 중단됐다. 혼합 사례는 선행
로컬 API를 1회 호출한 뒤 중단됐으며 결손만 있는 사례는 요청 0회였다. 소유한
검증 volume은 제거하고 부재를 확인했다.

이는 제공된 계약에 한정된 사례의 관측 결과다. 모델이 모든 미지원 요구를 발견한다는
증거나 임의 서비스·질의의 성공률이 아니며, 검토 승인도 결손을 구현 완료로 바꾸지 않는다.

## 값이 미정인 선택 필터의 추가·답변·철회

`trackRequestedApiInputs: true`와 선행 입력 범위 선택을 함께 켜고 원본 두 서비스
OAS의 188개 후보·등록 native 기능을 사용했다. 실제 Chomsky 10회 호출로 세 턴의
SDK JSON 생성과 격리 n8n 2.37.10 실행을 모두 통과했다. 응답 재생·재시도·실서비스
호출은 없었으며 평가기의 정답으로 모델 출력을 보정하지 않았다.

1. `회원번호 "fixture-member-01"의 간단 정보를 조회해줘.`
2. `조회 응답의 회원번호로 주소 목록도 가져와줘. addrType 필터도 적용해줘. 필터 값은 아직 몰라.`
   질문 후 `addrType은 문자열 "DEFAULT"야.`라고 답변했다.
3. `주소 조회에서 addrType 필터만 빼줘. 회원 조회와 응답 회원번호를 쓰는 주소 조회는 유지해줘.`

둘째 턴은 OAS의 선택 파라미터라도 요청한 입력으로 기록하고 실제 입력 질문에서
멈췄다. 답변 뒤에는 같은 API 계획을 사용했으며, 로컬 주소 요청에 필터와 선행 응답의
회원번호가 함께 전달됐다. 셋째 턴은 필터 값과 요청 의도를 철회하고 두 API·응답 참조를
보존했다. 세 실행의 로컬 요청 수는 1·2·2회였고 검증 volume은 제거 후 부재를 확인했다.

기록은 `.local-artifacts/canonical-short-evaluation/1792391606573-85750/`이다.
이 한 대화의 성공은 다른 서비스·모호한 질의에 대한 통계적 품질 보장이 아니다.
독립적인 타입·중첩·실행 전 차단 검사는 별도 통합 검사와 구현 장부에 기록한다.

2026-10-19 미배포 소스에서 두 기존 서비스의 원본 OAS 188개 작업과 등록된 native 기능 전체를 사용했다. 정답 API·입력값·바인딩은 평가기에만 두었고 모델 입력에는 질의·원본 OAS·실제 등록 기능을 전달했다. 정답으로 후보를 좁히거나 모델 출력을 고치지 않았다. 검토 승인은 명시적인 평가 사용자 동작이다.

## 전송 장애와 수정

최초 네 사례는 모두 첫 모델 호출에서 HTTP 400으로 중단됐다. 실제 API 후보는 188개였지만 동일한 근거 enum을 여러 출력 분기에 복사해 의미 분석 스키마에는 1,003개, 질문 스키마에는 1,185개로 집계됐다. 원본 스키마·오류는 `.local-artifacts/canonical-short-evaluation/1792379512489-45244/`에 보존했다.

선택·근거 스키마에는 Zod의 공식 `reused: 'ref'`를 명시해 같은 스키마를 공통 정의로 참조하도록 수정했다. API 후보·strict 검사·검증 규칙은 줄이지 않았다. [OpenAI 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs)는 전체 enum 값의 상한과 공통 정의 참조 지원을 명시하고, [Zod 문서](https://zod.dev/json-schema#reused)는 이 공유 설정을 설명한다.

모든 값 스키마에 이 옵션을 일괄 적용하지는 않았다. 별도 실험에서 Zod가 자동 정의를 만들면서 OAS 값 스키마가 이미 소유한 `$defs`를 덮는 현상을 재현했다. OAS 계약의 기존 참조 범위는 유지하고, 모델이 소유한 선택·근거 스키마에서만 공유 정책을 선택한다. 버전 감지나 오류 후 재시도·스키마 보정은 없다.

질문 스키마의 서로 다른 설명 필드가 같은 문자열 스키마의 메타데이터를 상속하면 draft-7 변환이 `allOf`를 만들고 모델 서버가 거절하는 문제도 확인했다. 텍스트 검사 생성 함수를 공유하되 설명 필드마다 독립적인 스키마를 만들었다. 검증·설명을 제거하거나 `allOf`를 사후 삭제하지 않았다. 큰 후보 목록의 실제 ChatOpenAI HTTP 전송·엄격한 후보 제한·설명 보존·기존 OAS 정의 범위를 회귀 검사한다.

중간 실행 `.local-artifacts/canonical-short-evaluation/1792379889049-46533/`에는 세 번의 평가 서버 실패와 질문 전송 실패를 보존했다. 평가 서버는 파라미터를 계약의 잘못된 위치에서 읽었다. 현재는 코드가 도출한 `effective.parameters`를 읽는다. 이 평가기 오류를 제품의 HTTP 매핑 실패나 모델의 API 선택 실패로 세지 않는다.

전체 기록은 `.local-artifacts/canonical-short-evaluation/1792380157343-47387/`에 있다. `frozen-cases.json`, `manifest.json`, `model-calls.json`, `outcomes.json`, `report.json`, 턴별 원래 상태와 `*.workflow.json`을 분리했다. 검증 Docker volume은 제거하고 없음을 확인했다. 앞선 개발 실행 4회·14회를 포함한 실제 모델 호출은 총 42회이며 이를 성공한 42개 사례로 세지 않는다.

## 남은 두 공백

1. 이 실행에서는 자연어 답변에서 모델이 JSON 문자열의 내부만 `sourceFormat: text`로 선택했다. 코드의 완전한 리터럴 경계 검사가 거절했고 값을 재작성하지 않았다. 이후 코드 소유 후보 선택으로 변경한 검증은 아래에 별도로 기록했다.
2. 생산자 선택 모델이 Merge의 실행 선행 노드를 설정값의 데이터 참조로 선언했다. 실제 Merge 설정에는 입력 수만 있어 참조 일치 검사에서 거절됐다. Assertion의 선언도 Merge를 데이터 생산자로 골랐지만 실제 필요한 값은 API 응답이다. 현재 선택 문맥에는 역할 설명·지시는 있으나 구현의 참조 위치 계약은 없다. 단순한 프롬프트 추가만으로 해결됐다고 보지 않으며, 실제 구현 계약에서 허용할 생산자 선택을 도출하는 보강이 남았다. 기존 참조 검사를 제거하거나 이 잘못된 계획을 통과시키지 않았다.

전체 검증·설치 기록과 기존 Ajv 합성 검사 상태는 [구현 장부](conversational-oss-implementation.md)의 최신 항목을 따른다. 이 평가는 제품 완성·배포를 선언하지 않는다.

## 원문 후보 선택으로 수정한 후속 실행

`analyzeApiInputAnswers`는 이제 모델이 `sourceText`·`sourceFormat`을 복사하게 하지 않는다. 코드가 완전한 JSON 후보와 따옴표 밖 텍스트 경계를 먼저 만들고 모델은 ID만 선택한다. 기존 원문·OAS 검사는 유지한다. 따옴표 내부를 고르거나 숫자의 일부를 잘라 선택하는 경계 자체가 제공되지 않는다. 인용되지 않은 문자열은 시작·끝 토큰으로 선택하며 원문 공백을 보존한다. 특정 필드명이나 OAS 타입에 맞춰 값을 추측하지 않는다.

같은 네 대화·12개 예정 턴을 한 번 더 실행했다. 실제 Chomsky 28회 호출로 9개 턴에 도달했고, 6개 턴의 SDK JSON은 격리 n8n 실행을 통과했다. 이전에 실패한 회원번호 답변도 실제 원문 후보 선택과 실행을 통과했다. 조회·뉴스레터 본문 변경·수정·취소 네 턴과 두 서비스 독립 조회도 통과했다. 실서비스 호출은 없으며 검증 volume은 제거 후 부재를 확인했다.

나머지 결과는 질문 보류 1개·실패 2개·미도달 3개다. 주소 추가는 회원번호 응답 바인딩을 올바르게 골랐지만 요청하지 않은 선택 필터 세 개의 입력 의도를 되물었다. native Merge는 실행 선행 노드를 설정 데이터 참조로 선언해 기존 검증기가 거절했다. 없는 이력 API는 다른 API로 대체하지 않았고, 해당 API가 없다는 이유와 함께 `no-change`를 반환했다. 그러나 질문·결손 표시 없이 빈 완료 상태로 끝나 평가 기준을 만족하지 못했다. 마지막 사례를 잘못된 API 실행이나 정상적인 결손 안내로 기록하지 않는다.

기록은 `.local-artifacts/canonical-short-evaluation/1792381347262-52087/`이다. 앞선 실행을 덮어쓰지 않았고 이번 원문 후보 수정이 전체 대화 품질을 해결했다고 보지 않는다. 완전한 JSON 후보·이스케이프·Unicode·숫자 문자열·배열·객체·역순과 다른 텍스트 구간 거절은 [후보 선택 검사](../test/api-input-source-selection.test.mjs)에서 확인한다. 최신 집중 42/42, 원본 OAS 47/47, 전체 회귀 1053/1054이며 전체 실패 한 건은 기존 Ajv 특수 키 합성 검사다. 독립 설치도 세 tarball·ICL 원본 34개 후보로 통과했다.

## native 참조 자격 계약 반영 후 실행과 그래프 갱신

같은 188개 작업·전체 native 후보와 고정된 네 대화를 새 참조 자격 계약으로 다시 실행했다. 실제 Chomsky 호출은 29회이며 12개 예정 턴 중 8개에 도달했다. 조회·뉴스레터 추가·값 수정·취소 네 턴과 두 서비스 독립 조회는 JSON 생성과 격리 n8n 실행을 통과했다. 한 턴은 입력 답변 뒤 추가 질문에서 멈췄고 두 턴은 실패했다. 후속 네 턴은 미도달이다. 정상 완료 5건만으로 전체 성공률을 계산하지 않는다.

native 결과 수집·응답 검사 턴은 생산자 선택과 설정·연결 계획을 지나 최종 검토까지 도달했지만, 정상 데이터의 n8n 실행 결과가 `success` 대신 `error`여서 실패했다. 이 기록만으로 실패 원인을 확정하지 않는다. API 부재 사례도 질문·결손 표시를 요구하는 기존 검사에서 다시 실패했다. 앞선 자연어 입력 답변 성공이 이번 실행의 추가 질문까지 해결했다는 뜻은 아니다.

자료는 `.local-artifacts/canonical-short-evaluation/1792383208454-57524/`의 `outcomes.json`과 턴별 원래 결과·워크플로우에 보존했다. 업무 API 호출은 0회이며 소유한 검증 volume은 제거 후 없음을 확인했다. [현재 그래프](current-conversation-graph.md)의 진행 안내도 이 관측 결과에 맞춰 갱신했다. 29개 노드·66개 등록 경로는 그대로이며 실행 실패 원인·추가 질문·빈 완료 처리는 미해결이다. 이번 그래프 갱신에서 제품 동작을 변경하거나 모델을 다시 호출하지 않았다.

## 독립 응답의 단일 item 증명 수정

위 native 실행 실패를 같은 JSON·로컬 계약 서버에서 재현했다. 두 API와 Merge는
정상 종료했고 Merge가 출력한 두 item을 받는 응답 검사에서 실패했다. 독립 분기를
append한 각 item에는 두 분기의 선행 관계가 모두 있지 않은데, 기존 응답 검사가
두 API 모두에 `itemMatching(inputIndex)`를 호출했다.

OSS n8n 컴파일러에 단일 Manual Trigger item과 실제 API fragment의 item 보존·
DAG 경로로만 단일 응답을 증명하는 검사를 추가했다. native IF·응답 검사는 증명된
API를 정확히 하나인 결과로 읽고, 증명하지 못한 API는 원래 item 선행 관계로 읽는다.
응답 0개·복수 결과는 실패하며 오류 후 첫 결과를 선택하는 경로는 없다. 모델 계획·
값·데이터 타입·OAS·선택 후보·업무 연결을 변경하지 않았다.

앞서 실제 Chomsky가 반환한 초안과 메시지를 그대로 읽고 원본 188개 OAS 작업과
등록 기능으로 다시 컴파일했다. 정상 데이터의 JSON은 격리 n8n에서 통과했다.
같은 JSON에서 로컬 회원 응답의 `code`만 `-7`로 바꾼 시험은 원래 모델이 정의한
`Member lookup response code must be numeric 0.` 메시지로 실패했다. 추가 모델
호출은 0회이며 새 생성 성공률로 세지 않는다. 재현 로그는
`.local-artifacts/native-collection-failure-replay.json`, 수정 후 JSON·실행 결과는
`.local-artifacts/native-singleton-real-model-*`에 보존했다.

별도 공개 API 기반 회귀는 [단위 검사](../test/native-singleton-response-readers.test.mjs)와
[격리 n8n 검사](../integration/native-singleton-responses-local-n8n.mjs)에 있다.
IF guard·비교식의 정책 일치, 잘못된 전체 응답의 OAS 거절, 단일 결과 0개·2개 거절,
미증명 반복 참조의 무우회도 검사한다. 원래 짧은 대화의 모든 턴을 새 모델 호출로
재평가한 것은 아니며, 추가 질문과 API 부재 시 빈 완료 처리는 여전히 남아 있다.

## 단일 노드 연결을 코드로 확정한 뒤의 실제 평가

준비된 단일·독립 노드의 암묵적 연결은 Core가 DAG 연결 0개임을 증명한다. 이 경우
연결 모델을 호출하지 않는다. 명시적인 연결 변경 요청, 여러 노드, join·참조 의존성과
미완료 작업은 기존 질문·계획·검토 경로를 유지한다. 빈 실제 변경 목록도 조립 단계가
원래 초안과 revision을 그대로 반환하며 새 빈 수정본을 만들지 않는다.

같은 원본 188개 작업·전체 native 후보·네 대화를 실제 Chomsky 33회로 평가했다.
예정 12턴 중 10턴에 도달해 8턴의 JSON·격리 n8n 실행이 통과했고, 없는 이력 API
사례는 예상한 질문에서 멈췄다. 짧은 회원 조회와 자연어 번호 답변은 연결 모델 없이
3회 호출로 완료됐다. 조회·뉴스레터 추가·수정·취소 네 턴과 두 서비스 조회·native
수집/검사 추가·상품 쪽 제거 세 턴도 통과했다. native 응답 검사의 정상·실패 변형도
실행했다. 기록은 `.local-artifacts/canonical-short-evaluation/1792385225658-64850/`다.

나머지 주소 추가 턴은 평가기가 `query: {}`와 `{}`를 서로 다른 리터럴 입력으로
보아 실행 전에 멈췄다. 실제 후보를 수정하지 않고 다시 컴파일·실행하니 두 API 호출과
원래 OAS 검사가 통과했다. query 필드는 전송되지 않았고 주소 요청 회원번호는 최초
리터럴이 아니라 앞선 응답에서 읽었다. 이 확인에는 모델을 다시 호출하지 않았다.

평가기에는 빈 named-parameter 묶음을 실제 입력 필드 없음과 같게 비교하는 별도
[검사 함수](../integration/utils/assert-api-literal-inputs-match.mjs)를 추가했다.
제품 데이터나 생성 JSON은 바꾸지 않는다. 본문 `{}`·`[]`·null의 존재, 개별 파라미터의
빈 객체·배열, false·0·빈 문자열과 타입 차이는 계속 구분한다.
[회귀 검사](../test/api-literal-input-comparison.test.mjs) 세 건이 이 경계를 확인한다.
원래 평가 보고서의 실패와 미도달 2턴은 덮어쓰지 않았다. 직접 실행 근거는
`.local-artifacts/single-node-connections-address-replay.json`에 있다.

원래 응답을 재생하는 시도는 6개 반환 뒤 일곱 번째 스키마 검사에서 중단됐다. 새 승인
기록의 UUID가 초안 지문과 다음 노드 ID를 바꾸므로 원래 연결 스키마를 그대로 쓸 수
없었다. ID를 바꾸거나 검사를 완화하지 않았으며 실제 모델 호출은 0회다. 해당 시도는
`.local-artifacts/canonical-short-evaluation/1792385554350-66315/`에 남겼다.

그 대신 원래 저장된 확정 초안과 대화 기록을 초기값으로 새 호스트 대화를 시작했다.
남았던 최초 회원번호 수정·주소 취소 두 턴은 실제 Chomsky 4회·격리 n8n 실행으로
통과했다. 기록은 `.local-artifacts/canonical-short-evaluation/1792385692187-66624/`다.
이 결과를 처음부터 새로 생성한 12턴 연속 통과로 합산하지 않는다. 알려진 한 묶음의
추가 관측이며 선택 입력 질문 정책이나 빈 `no-change` 완료 경로가 해결됐다는 뜻도
아니다. 모든 실행에서 업무 API 호출은 0회이고 소유한 검증 volume은 제거 후 부재를
확인했다. 수치 합격 기준은 정하지 않았다.

## 빈 결과의 완료 표시 수정과 원본 응답 재생

이전 `1792383208454-57524` 실행의 이력 조회 사례는 실제 워크플로우 없이
`complete`와 `exported`를 반환했다. Core의 빈 초안 준비 상태는 이미 false였으며,
호스트 예제의 최종 출력 상태가 잘못된 경우다. 현재 호스트는 실제 JSON 생성 시에만
`workflow-exported`를 반환하고, API·native 인스턴스가 없으면 `no-workflow`로 끝낸다.
이 결과만으로 API 부재나 사용자 요구 충족을 판단하지 않는다.

원본 188개 작업·native 후보와 당시 두 Chomsky 응답을 재사용했다. 각 단계의 이름·
출력 스키마·입력이 원본과 같은지 먼저 검사했으며 최종 계획·초안도 그대로였다.
이전의 빈 완료만 `no-workflow`로 바뀌었고, 실제 모델·업무 API·n8n 호출은 0회다.
기록은 `.local-artifacts/conversation-outcomes-original-model-replay.json`에 있다.
이전 실패 보고서를 덮어쓰거나 이를 새 생성 성공률에 합산하지 않았다.

정상 출력 경로도 `1792385225658-64850`의 회원 조회 두 응답을 같은 방식으로
재생했다. 계획·요청값을 유지한 SDK JSON은 격리 n8n 2.37.10에서 로컬 계약 서버를
한 번 호출하고 성공했다. 반환한 revision·준비 상태는 실제 artifact와 일치했다.
기록과 JSON은 `.local-artifacts/conversation-outcomes-exported-runtime.*`에 있다.
실제 모델·업무 서비스 호출은 없으며 소유한 검증 volume의 제거도 확인했다.

이는 출력 상태의 정직성을 검증한 결과다. 기능이 없을 때 필요한 질문·명시적 결손
계획을 항상 생성한다는 증거나 전체 짧은 대화의 재평가 결과는 아니다. 선택 필터 질문
정책과 넓은 품질 평가는 별도로 남아 있다.

## 선행 입력 범위를 고정한 실제 주소 조회 평가

정본 예제의 `planApiBindingInputs: true`는 선택된 API에서 선행 결과를 받을
입력 포인터를 먼저 고정한다. 이후 바인딩 모델은 그 입력만 연결하거나 질문할
수 있다. 범위를 벗어난 질문을 삭제하거나 기본값을 채우는 방식은 사용하지 않는다.
기존 옵션을 생략한 호출에 이 보장이 자동으로 생기는 것은 아니다.

원본 188개 작업과 등록된 native 후보를 유지한 두 대화·6턴을 실제 Chomsky
20회 호출로 평가했다. 모든 턴에서 SDK JSON 생성과 격리 n8n·로컬 계약 서버
실행이 통과했다. 업무 서비스 호출과 재생 응답은 0회이며, 검증 volume은 제거 후
없음을 확인했다. 새 평가 기록은
`.local-artifacts/canonical-short-evaluation/1792388745981-77299/`다.

첫 대화는 짧은 회원 조회, 자연어 회원번호 답변, 응답 회원번호를 사용하는 주소
추가, 최초 회원번호 수정, 주소 취소를 수행했다. 주소 추가 시 선택 필터 3개에
대한 불필요한 질문이 나오지 않았다. 두 번째 대화에서 사용자가 명시한
`addrType: "DEFAULT"`는 후속 주소 요청에 그대로 전송됐다. 두 주소 계획 모두
선행 데이터의 대상은 `/header/custNo`뿐이었고, 실제 값은 최초 입력이 아닌
회원 조회 응답에서 읽었다. 6회 실행의 로컬 요청은 총 9회다.

알려진 계약·고정 질의의 한 번의 실행이며 일반 생성 성공률로 확대하지 않는다.
요청한 선택 리터럴 값이 아직 없는 경우의 질문 정책은 남아 있다. 첫 선택의 의미
정확도나 모든 설명의 한국어 출력도 코드 검증만으로 보장하지 않는다. 실제 첫
주소 계획의 의도 설명은 영어였다. 전체 회귀의 기존 Ajv 실패와 로컬 HTTP 연결
오류는 [구현 장부](conversational-oss-implementation.md)에 따로 기록했다.
